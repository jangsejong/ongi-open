## 1. 기능 정의

- 사용자 대면 = 온기 홈의 큰 **"도와주세요"** 버튼 / 문서상 **보호자 통화 코칭** / 내부 `guardian_coaching`.
- **한 문장**: 어르신이 버튼 하나를 누르면 사전 등록된 보호자와 통화가 연결되고, 보호자가 어르신 화면을 보며 단계적으로 알려 주고, **화면 조작은 어르신이 직접 한다**.
- **보호자가 얻는 능력은 딱 둘 — 보는 것과 말하는 것.** 기기로 들어오는 쓰기 경로는 만들지 않는다(ADR-16).
- **감시 도구가 아님을 정의로 못박는다**: 상시 수집 0 / 세션 종료 시 접근 소멸 / 위치·통화·문자·연락처·앱 사용기록 전송 0 / 화면 녹화·저장 0 / 통화 녹음 0 / `IsMonitoringTool` 메타데이터 **미선언**.
- **문구 규율**: "원격 통제", "원격 감시", "원격 관리" 표현을 쓰지 않는다 — 앱 문구·Play 스토어 설명·결과보고서·마케팅 전부 동일하게 적용한다. 대체 표현은 "도움", "코칭", "알려 주기".

### 이 정의가 설계를 근본적으로 단순하게 만든다

원격 조작을 하지 않기로 하면, 원격 제어 기능이 통상 부딪히는 장벽이 대부분 소멸한다.

| 제약 | 근거 | 이 설계에서 |
|---|---|---|
| 타인 기기 원격 접근의 접근권한 | 정보통신망법 제48조① — "누구든지 정당한 접근권한 없이 또는 허용된 접근권한을 넘어 정보통신망에 침입하여서는 아니 된다"(위반 시 5년 이하 징역 또는 5천만원 이하 벌금) | **불성립** — 기기에 대한 원격 접근이 0이다. 어르신 기기가 화면을 송출할 뿐이고, 들어오는 명령 채널이 없다 |
| 성인 대상 감시는 동의가 있어도 Play 금지 | Play Malware/Stalkerware 정책. 허용 예시는 *"parents to monitor their children"*·기업의 임직원 관리뿐이고, *"cannot be used to track anyone else (a spouse, for example) **even with their knowledge and permission**, regardless if persistent notification is displayed"* | **해소** — 상시 수집이 없고 어르신이 개시·종료하는 통화 세션이다. 자녀→노부모는 정책의 허용 예시에 없으므로, **감시 성격으로 포지셔닝하면 Play 출시가 봉쇄된다** → 문구 규율이 정책 요건이다 |
| 화면 조작은 AccessibilityService가 유일 경로 | Play가 "앱이 자율적으로 액션을 개시·계획·실행"하는 Accessibility API 사용을 금지. `isAccessibilityTool=true`는 장애인 접근성 목적만 적격 | **회피** — 조작을 하지 않는다. **ADR-10(1차 릴리스 제외) 번복 불필요** |
| 기기 정책 통제는 Device Owner 필요 | 공장초기화 상태에서의 프로비저닝이 필요 → 이미 사용 중인 폰에 사후 설치로 획득 불가. Google의 device admin deprecation 문서는 **소비자 앱용으로 화면 잠금·원격 초기화만 계속 제공**한다고 명시하고(Find My Device 유형), 키가드·비밀번호 정책은 deprecated로 분류한다 — 앱 차단·설정 잠금 같은 실질 통제는 남아 있지 않다 | **불필요** — 통제하지 않는다 |
| 화면 공유는 정보 노출 | Android 14+ MediaProjection은 **캡처 세션마다** 시스템 동의를 강제하고 `mediaProjection` foreground service type을 요구 | **OS가 게이트를 대신 강제** — "그 순간만"을 플랫폼이 보증한다 |

> 출처(대표): support.google.com/googleplay/android-developer Malware 정책(9888380) Stalkerware 절·AccessibilityService API(10964491), developer.android.com/about/versions/14/behavior-changes-14 `#media-projection-consent`, developer.android.com/media/grow/media-projection, developers.google.com/android/work/device-admin-deprecation, law.go.kr 정보통신망법 제48조.

## 2. 본인인증의 3중 재배치 (이 문서의 핵심 논지)

원안은 본인인증을 세션 진입 조건으로 두었다. 그러면 **본인인증조차 어려운 사람이 배제되는데, 그 사람이 정확히 온기의 주 타깃**이다. 그래서 위치를 옮긴다.

| 위치 | 목적 | 수행 주체 |
|---|---|---|
| 사전 등록 시 1회 | 어르신·보호자 실명 **명의 대조** | 통상 보호자가 대리 수행(§8 ADR-12 ① 관례) |
| **코칭 과업 #1** | 어르신이 **배우는 대상** | 어르신이 보호자 코칭을 받아 직접 |
| ~~세션 진입 조건~~ | **제거** | — |

**왜 세션 개시에 인증을 두지 않아도 되는가** (ADR-17 근거):

1. **위임되는 권한이 0이다.** 인증은 권한 위임을 보호하는 장치인데, 이 세션에서 보호자에게 넘어가는 권한이 없다. 지켜야 할 대상이 없으면 게이트도 필요 없다.
2. **인증을 조건으로 두면 주 타깃이 배제된다.** 지문 미등록·PIN 망각·PASS 미설치 어르신이 도움을 가장 필요로 한다.
3. 개시 게이트는 두 개로 충분하다 — ① **기기를 물리적으로 쥔 사람의 1탭** ② 연결 대상은 **사전 등록·승인된 보호자뿐**.
4. 제3자가 어르신 폰에서 버튼을 눌러도 **등록 보호자에게 연결**되므로 공격자에게 이득이 없다(오히려 신고 효과가 난다).
5. 정보 노출(화면 공유)에 대한 게이트는 **OS가 강제**한다(Android 14+ 세션별 동의).

## 3. 게이트 구조

| 단계 | 게이트 | 주체 | 빈도 |
|---|---|---|---|
| 사전 A | 보호자 등록 — **연락처를 미리 특정해 기입** + 실명 본인확인 명의 대조 + 등록 앱 인스턴스 바인딩 | 어르신 기기(보호자 대리 허용, 단 어르신 확인 화면 필수) | 보호자당 1회 |
| **사전 A′** | **등록 변경 보호** — 연락처 수정·보호자 추가·해제는 **어르신 본인 확인 없이는 불가**(생체/잠금 자격증명). ~~변경 시 어르신과 기존 등록 보호자 전원에게 통지~~ ← **미구현**(§14 미결) | **어르신만** | 변경마다 |
| 사전 B | 관계 증빙 서류 + 관리자 승인(유효기간 있음) | 보호자 제출 · 운영자 검증 | 1회 + 갱신 |
| **세션 C** | **"도와주세요" 1탭 — 인증 없음** | **어르신**(기기 물리 점유) | 세션마다 |
| 세션 D | 요청 수락 → 통화 연결 | 보호자 | 세션마다 |
| 세션 E | 화면 공유 OS 동의 — **선택**(통화만으로도 성립) | 어르신 | 세션마다(OS 강제) |
| 세션 F | 민감 화면 정책(§6) | 어르신 / 시스템 | 화면 진입마다 |

- 어르신은 언제든 사전 A를 해제(보호자 등록 취소)하고, 세션 중에는 1탭으로 끝낼 수 있다.
- **서버·관리자는 어떤 단계에서도 세션을 열 수 없다.** 세션은 어르신 기기에서만 시작된다.
- 세션 E를 거치지 않으면 통화만 이루어진다 — 화면 공유는 항상 별개의 선택이다.

### 사전 A′가 낯선 사람 경로를 닫는다 (ADR-21)

**연락처를 미리 특정하고 그 번호를 본인 아니면 바꿀 수 없게 하면, 사칭 피싱범이 이 기능을 발판으로 접근하는 경로가 없어진다.** 등록되지 않은 사람은 세션 대상이 될 수 없고, 등록 목록을 바꾸려면 어르신 본인 확인을 통과해야 한다. 온기가 새로운 피싱 채널이 되는 것을 구조로 막는 것이 사전 A′의 목적이다.

**등록 변경에는 본인 확인을 요구하는 이유** — 세션 개시(세션 C)에는 인증을 두지 않는데 여기에는 두는 것이 모순이 아니다. §2의 기준을 그대로 적용한 결과다: **등록 변경은 지속적 자격을 부여하는 실제 권한 위임이므로 지킬 대상이 있고, 세션 개시는 위임되는 권한이 0이라 지킬 대상이 없다.** 게이트는 권한이 있는 곳에만 둔다.

**단, 전화번호 자체를 신뢰 근거로 쓰지 않는다.** 발신번호 거짓표시는 전기통신사업법 제84조의2로 금지되고 제95조의2 제4호에 따라 3년 이하 징역 또는 1억원 이하 벌금 대상이지만, 변작기 제조·수입·배포까지 전면 금지로 규제가 계속 강화되는 것이 실제로 발생한다는 방증이다. 그래서 신뢰 앵커를 다음에 둔다:

| 항목 | 신뢰 근거 |
|---|---|
| 통화 | 발신번호 — **보조 수단**. 위조 가능하므로 이것만으로 세션이 열리지 않는다 |
| **세션(화면 공유)** | **등록된 앱 인스턴스** — 릴레이가 등록 보호자의 상시 소켓으로 보낸 요청에 그 앱이 등록 시 교환한 키로 응답해야만 성립한다(구현은 FCM 대신 자체 WebSocket). 발신번호만 위조하면 통화는 올 수 있으나 **화면 공유는 열리지 않는다** |
| 어르신 화면 표시 | "등록된 ○○○님 앱에서 연결되었습니다" — 번호 일치가 아니라 앱 바인딩 확인 결과를 보여준다 |

> 출처: law.go.kr 전기통신사업법 제84조의2·제95조의2, KISA 발신번호 거짓표시 대응(kisa.or.kr/1020602).

## 4. E2E 플로우 (어르신 탭 수 최소화)

```
[1] 어르신: 온기 홈의 큰 "도와주세요" 1탭            ← 인증 없음. 여기가 세션 개시
[2] 등록 보호자 폰: 릴레이 소켓으로 요청 수신 → 보호자 모드가 코칭 화면으로 전환
                                              ← ⚠️ 현재는 보호자 앱이 떠 있어야 받는다(§8 미결)
[3] 보호자: 수락 → 보호자 폰이 발신(ACTION_DIAL) → 어르신은 "받기"만
[4] 보호자: 통화로 "화면 보여주실 수 있어요?" 안내 → 어르신 큰 버튼 1탭 → OS 동의 다이얼로그
[5] 보호자: 화면을 보며 단계별로 말로 알려 준다 — 화면 조작은 전부 어르신 손
[6] 종료: 어르신 1탭 또는 통화 종료 → 공유 즉시 소멸 → 요약 화면
```

- **어려운 단계를 사람이 말로 도와주는 것이 이 기능의 강점이다.** [4]의 OS 동의 다이얼로그는 어르신 혼자면 실패하지만, 통화가 이미 연결된 상태에서 보호자가 안내하면 통과한다. 그래서 **통화 먼저 → 화면 공유 나중** 순서를 설계상 반드시 지킨다.
- 등록 보호자가 1명이면 [1]에서 대상 선택 화면을 생략한다. 2명 이상이면 사진+이름 큰 타일로 고른다.
- 어르신 쪽 필수 동작은 **탭 3회**(도와주세요 → 전화 받기 → 화면 보여주기)이고, 이 중 2회는 통화로 안내를 받는 상태에서 이루어진다.

## 5. 단계적 코칭 = 과업 템플릿

보호자 모드에 과업별 **단계 체크리스트 + 흔한 실수 메모**를 넣는다. 보호자가 처음 도와주더라도 헤매지 않게 하는 것이 목적이고, 이 템플릿 자체가 온기의 콘텐츠 자산이 된다.

## 6. 민감 화면 3단 정책

본인인증 코칭이 목적이라면 인증 앱 화면을 보호자가 봐야 한다. 그런데 그 완화가 경제적 착취의 통로가 되어서는 안 된다. 그래서 등급을 셋으로 나눈다.

| 등급 | 대상 | 정책 |
|---|---|---|
| **재동의 후 허용** | 인증(PASS 등)·정부24·병원·공공 | 진입 시 **자동 가리기** → 어르신이 재동의 1탭을 하면 공유 재개. 본인인증 코칭 목적을 달성한다 |
| **전면 차단** | 은행 이체·송금·결제·간편결제 | 진입 시 자동 가리기, **재동의 경로를 만들지 않는다**. §5 코칭 과업 목록에서도 제외한다 |
| **상시** | 전 세션 | 경고 배너 "비밀번호·인증번호는 보호자에게도 보여주지 마세요" + 어르신이 언제든 누를 수 있는 **"가리기"** 버튼 상시 노출 |

- 판정 기반: 기존 `LifeCategory`(`app/lib/core/config.dart` 14종) + 카테고리 사전(`app/lib/features/apps/category_rules.dart`) 재사용. 구현은 `app/lib/features/coaching/share_policy.dart`의 순수 함수 `sharePolicyFor`.
  - 카테고리 v2가 금융을 은행/카드·페이/증권·보험으로 쪼개 두어(v0.0.13) 이 셋은 **카테고리만으로 전면 차단**된다.
  - 분류가 아직 안 된 앱은 패키지명·라벨의 금융 신호(은행·페이·결제·bank·pay…)로 한 번 더 거른다 — **미탐이 곧 금전 피해라 넓게 잡고, 오탐은 화면이 가려질 뿐이다**(default-deny).
  - ⚠️ 남는 한계는 카테고리 세분화가 아니라 **판정 단위가 앱이라는 것**이다. 쇼핑·배달 앱 안의 결제 단계처럼 "금융이 아닌 앱의 결제 화면"은 구분하지 못한다(§14 미결).
- 포그라운드 앱 감지: `UsageStatsManager queryEvents` ACTIVITY_RESUMED(기존 `app/lib/features/routine/usage_repository.dart` 재사용).
  ⚠️ **감지 지연이 그대로 노출 시간이 된다** → 상한을 실측으로 확정해야 한다(§14 미결).
- 세션 이력에 "민감 화면 공유 있었음"을 기록한다(사후 감사).

## 7. 세션 모델

- 상태기계 `idle → requested → talking → sharing(선택) → ended` — `ModelManager`(`app/lib/features/model/model_manager.dart:16-33` phase enum + `:166-169` `_set`) 패턴을 복제했다. 설계 때 두었던 `connecting`은 구현에서 뺐다(수락 응답이 오면 곧바로 `talking`이라 중간 단계가 사용자에게 보일 일이 없다). 구현은 `app/lib/features/coaching/coaching_controller.dart`의 `CoachingPhase`.
- 종료 트리거: 어르신 1탭 / 통화 종료 / 앱 강제 종료 / 네트워크 단절 → **공유 즉시 소멸**.
- 가시성: 공유 중 상시 상단 배너(대비 7:1, 끝내기·가리기 버튼 60dp+) + foreground service 시스템 알림 + OS 화면 공유 인디케이터. **시스템 알림은 Android 13+ `POST_NOTIFICATIONS` 위에 선다** — 권한을 받는 자리와 그 이유는 §14(v0.0.24 항목).
- 감사 로그: 신규 sqflite `assist_sessions`(보호자·시각·통화 길이·공유 여부·민감 화면 접촉 여부). **화면 내용은 저장하지 않는다.** 보관 90일, 어르신이 보는 "도움받은 기록" 화면 제공.

## 8. 통화 = PSTN, 보호자가 발신 (ADR-18)

- **어르신은 전화를 받기만 한다** — 가장 익숙하고 실패율이 낮은 동작이다. 어르신이 발신하면 다이얼러에서 통화 버튼을 한 번 더 눌러야 하므로 그 부담을 없앤다.
- `ACTION_CALL`(즉시 발신, 위험 권한)은 쓰지 않는다 → `10_product_design.md` §4.2 원칙 유지. 보호자 모드에서 `ACTION_DIAL`(기존 `IntentActionsApi.openDialer` 재사용)로 건다.
- 앱 내 VoIP는 배제한다: 통화 품질·에코 취소·TURN 비용·어르신 익숙도 모두 불리하다.
- **통화는 신뢰의 근거가 아니다** — PSTN을 쓰는 대가로 발신번호 위조 가능성을 안게 되므로, 세션(화면 공유)은 등록 앱 인스턴스 검증으로만 열린다(§3 ADR-21). 번호가 일치하더라도 앱 바인딩이 확인되지 않으면 화면 공유 요청 화면 자체가 뜨지 않는다.
- ⚠️ **미검증 전제 2건** (§14 스파이크 항목):
  1. **PSTN 통화 중 MediaProjection 동시 동작** — `mediaProjection` foreground service가 앱이 백그라운드로 가도 공유를 유지한다는 문서 근거는 있으나, 통화 UI 점유·스피커폰 전환 UX는 실기기에서 확인하지 못했다. **이 전제가 깨지면 §8 전체(통화 방식)를 재설계해야 한다.**
  2. **보호자 앱 자동 기동 — 미해결.** FCM을 쓰지 않기로 하면서(외부 서비스 의존 0) 요청 전달이 릴레이 소켓 하나로 합쳐졌는데, **소켓을 살려 둘 포그라운드 서비스가 보호자 쪽에 없다.** 즉 지금은 보호자 앱이 떠 있을 때만 요청이 도착한다. 선택지는 (a) 보호자 모드 전용 FGS 추가, (b) FCM 재도입(의존 0 원칙 후퇴), (c) 어르신에게 "보호자가 앱을 열어 두어야 한다"고 안내. `USE_FULL_SCREEN_INTENT` 자동 전체화면 수신은 Android 14+에서 통화·알람 앱만 기본 허용이라 적격 여부 확인이 필요하고, 대안인 Telecom self-managed ConnectionService는 구현 부담이 크다.

## 9. 역할 모드 — 온기 1개 앱 (ADR-20)

- 설치 직후 "제가 어르신이에요 / 보호자예요"를 고르게 하고 `settings` KV(`app/lib/core/db.dart:90-109`)에 저장한다. 나중에 전환 가능.
- **보호자 모드는 2.6GB 모델 다운로드와 RAM 게이팅을 생략한다** — `10_product_design.md` §8 [3] 분기.
- 보호자 모드 UI는 시니어 제약(본문 22sp·터치 60dp·대비 7:1)을 면제한다 → `ongiTheme()` 분기 필요(§14 미결).
- 공유 자산: pigeon 네이티브 모듈, 통화, 화면 수신, DB, 인증.
- 별도 보호자 앱을 만들지 않는 이유: repo 1개·SBOM 1개·배포 1개로 팀 2명의 유지보수 부담을 절반으로 두고, 어르신이 나중에 보호자가 되는 전환도 자연스럽다.

## 10. 아키텍처 (v0.0.20 구현 완료 — 출품 범위 밖)

> 이 절은 착수 전 설계였고, 지금은 구현된 것을 기술한다. 실제 코드는
> `app/lib/features/coaching/`(어르신·보호자 양쪽 상태기계, 화면 공유, 페어링)과
> `server/main.py`(FastAPI WebSocket 릴레이 + `server/test_relay.py` 회귀 테스트)에 있다.

> 백그라운드 `<service>`**이고, **FCM/푸시·딥링크·`@FlutterApi` 콜백은 끝내 만들지 않았다**
> (요청 전달을 릴레이 한 채널로 합쳐 외부 서비스 의존을 0으로 유지했다).

  DB도 쓰지 않는다 — 메모리에 두는 것은 지금 붙어 있는 소켓의 기기 키와 페어링 자격뿐이고 연결이 끊기면 사라진다
  (워크스페이스 표준 스택의 Postgres는 저장할 것이 없어 채택하지 않았다).
- 화면 전송은 P2P 우선. ⚠️ NAT 통과용 TURN이 필요해지면 egress 비용이 발생한다 → `10_product_design.md` §2의 CDN 선정 기준(egress 무료)과 같은 민감도로 다룬다(§14 미결).
- 매니페스트 추가(v1.2): `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PROJECTION`, `mediaProjection` foreground service type `<service>`. 기존 `POST_NOTIFICATIONS` 재사용.
  **`QUERY_ALL_PACKAGES`·`BIND_ACCESSIBILITY_SERVICE`·`BIND_DEVICE_ADMIN`은 계속 선언하지 않는다.**
- 데이터 모델 추가: `guardians`(별칭·연락처·승인 상태·유효기간), `assist_sessions`.

## 11. 남용 방어 — 무엇을 막고 무엇을 못 막는가

| 공격 | 차단 | 수단 |
|---|---|---|
| 보호자가 원격에서 몰래 세션을 여는 것 | ✅ | 개시는 어르신의 물리 1탭뿐. 보호자·서버·관리자에게 개시 경로가 없다 |
| 보호자가 기기를 조작하는 것 | ✅ | **쓰기 경로 0** — 명령 채널을 만들지 않는다(ADR-16) |
| 미등록자가 연결되는 것 | ⚠️ 부분 | 등록된 앱 인스턴스 키로만 세션이 성립한다(ADR-21). **다만 릴레이는 키의 소유를 증명받지 않는다** — 접속 쿼리로 주장한 키를 그대로 신원으로 쓰고, 기본 주소가 평문 `ws://`라 경로상에서 키가 보인다. 키를 알아낸 사람은 정당한 기기를 밀어내고 그 신원을 차지할 수 있다(§14 미결). 또 **사전 B(관계 증빙 + 관리자 승인 콘솔)는 미구현**이고 보호자 본인의 페어링 수락이 그 자리를 대신한다(§14 미결) |
| **사칭 피싱범이 이 기능으로 어르신에게 접근하는 것** | ✅ | **연락처를 미리 특정**하고 등록 목록 변경에 어르신 본인 확인을 요구한다(사전 A′·ADR-21) — 등록되지 않은 사람은 세션 대상이 될 수 없다 |
| 몰래 보호자를 추가·연락처를 바꿔치기하는 것 | ⚠️ 부분 | 사전 A′ — 목록을 바꾸는 모든 경로에 어르신 본인 확인(잠금 자격증명)이 걸린다. **다만 "기존 등록 보호자 전원에게 통지"는 미구현**이다(설계 의도였고 코드에 없다 — §14 미결). 지금 막는 것은 본인 확인을 통과하지 못하는 변경까지다 |
| **발신번호를 위조해 등록 보호자로 사칭하는 것** | ✅ | 신뢰 앵커가 번호가 아니라 **등록 앱 인스턴스**다(ADR-21) — 번호를 위조해도 통화만 오고 화면 공유는 열리지 않는다. 앵커 자체를 노리는 경로(키 위조·코드 선점)는 위 "미등록자" 행에서 다룬다 |
| 페어링 코드를 선점해 앵커를 가로채는 것 | ✅ | 코드는 키 앞 6자라 **키를 그 코드에 맞춰 만들어 접속하면** 어르신의 코드 대조(같은 6자)를 통과한다. v0.0.23에서 릴레이가 같은 코드로 풀리는 다른 키의 접속을 거절하고(`code_conflict`), 코드가 모호하면 아무에게도 이어 주지 않는다. 남는 것은 선점자가 진짜 보호자의 접속을 막는 방해(가로채기가 아니라 실패)다 |
| 제3자가 어르신 폰에서 버튼을 누르는 것 | ✅ 무해 | 등록 보호자에게 연결되므로 공격자 이득 0(신고 효과) |
| 송금·결제 화면 훔쳐보기 | ✅ | 전면 차단, **재동의 경로 없음**(§6) |
| 세션 종료 후 잔존 접근 | ✅ | 어느 쪽이 끝내든·끊기든 공유가 즉시 소멸한다, 저장 0. v0.0.22에서 이 보증을 깨던 경로 넷을 막았고(보호자 끊기 미전달, 스테일 핸들러의 세션 파괴, 뒤로가기 시 단계 고착, 동의 중 종료 시 고아 캡처), v0.0.23에서 **재접속으로 밀려난 연결이 세션을 물고 놓지 않던 경로**를 막았다(상대에게 종료를 알리고 링크를 푼다) |
| 인증 화면의 비밀번호·인증번호 노출 | ⚠️ 완화 | 재동의 + 상시 경고 배너 + "가리기" 1탭 + 이력 기록 |
| **등록 보호자 본인이 말로 속이거나 압박하는 것**(가족 간) | ⚠️ 완화 | **익명성이 없다** — 누가 했는지 특정되고 세션 이력이 남는다. + 송금·결제 코칭 제외·전면 차단(ADR-19) + 조작 권한 0 + 다른 등록 보호자에게 통지 옵션 |
| 강압(옆에서 지문을 대게 하거나 시키는 경우) | ❌ **기술로 불가** | 사후 방어만: 이력·통지·이상 빈도 경고 |

**낯선 사람 경로는 닫혔고, 남는 것은 등록된 사람의 오용이다.** 사전 A′(연락처 사전 특정 + 변경 보호)와 앱 인스턴스 바인딩으로 사칭·피싱 벡터가 제거되므로 이 기능은 보이스피싱의 발판이 되지 않는다. 남는 것은 **이미 등록된 보호자 본인이 악용하는 경우**이고, 이는 성격이 다른 리스크다 — 보건복지부 노인학대 현황보고서 기준 학대 행위자는 배우자 39.4%·아들 23.5%(2025년)로 친족이 다수여서 무시할 수 없다. 다만 이 설계에서는 **익명성이 없고(누가 했는지 특정), 조작 권한이 0이고, 송금·결제가 차단되고, 이력이 남는다** — 피싱의 핵심 자산인 익명성이 제거되므로 "사기"보다 "가족 간 분쟁·착취"의 영역으로 성격이 바뀐다. 기술이 끝나는 지점이 어디인지 명시하고, 코칭 과업에서 송금·결제를 빼는 것을 1차 방어선으로 삼는다(§6·ADR-19).

  - 지금 이름이 역할을 정확히 말한다 — 이 계층이 하는 일은 시그널링이다. 구현체가 하나뿐인 상태에서 이름을 바꾸거나 인터페이스를 넓히면 복잡도만 는다. `Mock`은 이미 테스트 대역 7개로 존재하며, 각 테스트가 필요한 동작이 달라 하나로 합칠 실익도 없다(출하 코드에 테스트 발판을 넣는 것이기도 하다).
  - **추상화 우선순위가 높은 곳은 시그널링이 아니라 미디어다.** `ScreenShare`는 인터페이스 뒤에 있지 않고 `help_screen`이 직접 생성하며, `ScreenShare`·`GuardianController` 둘 다 `createPeerConnection`을 직접 부른다. v0.0.24에서 캡처 시작 순서를 고칠 때 테스트를 위해 `requestConsent` 주입점을 따로 뚫어야 했던 것이 이 결합의 증상이다. 다만 두 번째 구현이 없는 상태에서 인터페이스를 먼저 그리면 대개 틀린 모양이 나오므로, **실제로 무엇으로 바꿀지 정해질 때** 그 모양에 맞춰 뽑는다.
  - 착수 조건: 두 번째 전송 구현 요구가 실제로 생기거나(예: 아래 Cloudflare 이전), 미디어 계층을 손대게 될 때.

  - **지금 하지 않는 이유**: 코칭은 출품 범위 밖이고 마감이 8/27이다. 그리고 아래대로 "그대로 옮기기"가 아니라 재설계라 시간이 든다. 대신 대회 전에는 이전을 쉽게 만드는 것만 해 뒀다 — 주소를 코드에서 빼고(v0.0.25), 전송 계층을 `CoachingSignaling` 뒤에 두고, 주소 해석을 전송 계층 안으로 넣었다. 옮길 때 앱에서 고칠 것은 구현 클래스 하나다.
  - **왜 Firebase가 아닌가**: §0이 기록한 대로 FCM에서 자체 WebSocket으로 옮겨 온 이유(`google-services.json` 대기 지점 제거, 외부 서비스 의존 0)를 그대로 되돌린다. 5년간 Public이어야 하는 저장소에 프로젝트별 설정이 들어가고, Play Services SDK 의존이 붙어 "온디바이스·외부 의존 0"이라는 이 앱의 주장과 부딪힌다.
  - **왜 Cloudflare인가**: Workers는 HTTPS/WSS만 받으므로 아래 평문 `ws://` 항목이 이전만으로 닫힌다. 공개 엔드포인트라 사내망 접근 문제가 사라진다.
  - **그대로 옮길 수 없는 지점**: 지금 릴레이는 전역 레지스트리이고 `by_code`가 접속 중인 모든 피어를 훑는다. DO는 이름으로 인스턴스를 잡는 모델이라 이 스캔이 매핑되지 않는다. DO 이름을 페어링 코드로 쓰려면 **코드가 기기 키 파생이 아니라 서버 발급 1회용 값**이어야 하고, 그게 마침 코드 선점 문제(v0.0.23은 "겹치면 접속 거절"로 막았을 뿐 방해는 남는다)의 근본 수정이다. 이전과 함께 처리한다.
  - **TURN은 별도 판단**: Cloudflare Realtime은 SFU와 별개로 **P2P 전용 TURN**을 제공하고("point-to-point connection between two peers ... without any server-side media processing"), 요금은 아웃바운드 $0.05/GB에 1,000GB 무료다(SFU와 함께 쓰면 무료). 단 표준 `iceServers` 설정만으로 붙는지는 공개 문서에서 확인하지 못했다 — 자격증명은 "credential generation endpoint"가 RFC 초안 형태의 JSON을 돌려준다고만 돼 있다. **TURN 도입을 확정하기 전에 이 두 가지(표준 클라이언트 호환·자격증명 발급 방식)를 실측할 것.** coturn 자체 운영·타 업체도 후보로 남긴다. 관련 미결은 아래 "화면 전송 경로 P2P vs TURN".
  - 출처: developers.cloudflare.com/realtime/turn/ · /realtime/turn/faq/
- [ ] **릴레이가 기기 키의 소유를 증명받지 않는다** — 접속 쿼리로 주장한 키를 그대로 신원으로 쓰고, 같은 키로 오면 기존 소켓을 밀어낸다. 키 하나면 그 기기로 가장할 수 있다(§11 "미등록자" 행을 ⚠️로 내린 근거). 필요한 것은 챌린지-응답(키로 서명한 nonce)이다.

  - **v0.0.30 정정 — v0.0.28의 설정 폴백은 두 경우를 놓치거나 다치게 했다.** ① Android 13+ **영구 거부(2회 거부)** 상태는 `checkSelfPermission`상 "요청 가능"으로 보여 요청 경로를 탔는데, 그 요청은 UI 없이 즉시 거부된다 — "알림 켜기"를 눌렀는데 아무 일도 없는 막다른 탭(폴백이 있어도 이 분기에는 닿지 않았다). ② 같은 메서드를 쓰는 **모델 다운로드**는 반대로 폴백이 해가 됐다 — 알림이 차단된 기기에서 다운로드를 시작하면 설정 화면으로 끌려갔다. 수정: `canRequestPostNotifications()`(pigeon 신설)가 **팝업 가능 여부를 사전 판별**하고 — 영구 거부와 "아직 안 물음"은 둘 다 rationale이 false라 네이티브가 요청 이력(SharedPreferences)을 남겨 가른다 — 불가 시의 대안은 호출부가 맥락으로 정한다: "알림 켜기"는 설정 딥링크(사용자가 켜겠다고 한 순간), 모델 다운로드는 조용히 건너뛰기(기회성 요청). `requestPostNotifications()`의 일괄 설정 폴백은 제거. 잔여 한계: 구버전에서 이미 2회 거부한 채 업그레이드한 기기는 이력이 없어 첫 "알림 켜기" 1탭이 헛돌 수 있다(그 탭이 이력을 남겨 다음 탭부터 설정으로 간다 — 자가 치유).
